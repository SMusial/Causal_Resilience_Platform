# Design — Causal Resilience Intervention Allocator (V1, Reconciled)

## 1. Product purpose

An educational causal-inference platform and decision-intelligence demonstration built around one synthetic telecom incident-response world. It teaches the difference between prediction, causal estimation, counterfactual simulation, policy evaluation, and constrained allocation.

V1 is Python-only and deliberately focuses on foundational static causal inference. It contains a realistic dynamic simulator, but does not claim to estimate longitudinal causal effects.

## 3. Design principles

1. One operational world, many lessons.
2. Define the causal question and estimand before selecting an estimator.
3. Treat the simulator's ground truth as a teaching oracle, never as an observed input to estimators.
4. Show warnings instead of manufacturing precise answers when assumptions or overlap fail.
5. Keep prediction, causal estimation, simulation, and allocation as separate layers.
6. Make provenance and uncertainty visible with every result.
7. Never use color as the only information channel.

## 4. Canonical V1 causal estimand

### Target trial

* Population: eligible synthetic incidents at `time_zero`.
* Treatment strategy 1: execute the fixed `COORDINATED_RESPONSE` protocol at `time_zero`.
* Treatment strategy 0: execute the fixed `MONITOR_REASSESS` protocol at `time_zero`.
* Follow-up: 24 hours after `time_zero`.
* Primary outcome: `customer_impact_minutes_24h`.
* Secondary outcome: `sla_breach_24h`.
* Primary estimand: ATE, `E[Y(1) - Y(0)]`, for the eligible incident population.
* Direction: negative values indicate fewer customer-impact minutes under coordinated response.

The estimand is static even when the outcome is generated by a dynamic trajectory after time zero.

## 5. Domain model

### 5.1 Incident episode

```python
IncidentEpisode(
    episode_id: str,
    baseline_covariates: BaselineCovariates,
    disturbance: Disturbance,
    initial_state: CaseState,
    treatment: BinaryTreatment,
    operational_protocol: Action,
    state_history: list[CaseState],
    action_history: list[Action],
    outcomes: OutcomeSet,
    censoring: CensoringIndicator,
    provenance: Provenance,
    ground_truth: GroundTruth | None,
)
```

`ground_truth` is available only in explicit teaching or test mode. `operational_protocol` records the simulated protocol; `treatment` records the primary binary contrast.

### 5.2 Baseline covariates

At minimum:

* disturbance type and severity;
* topology criticality and redundancy;
* affected customers and service impact;
* asset health and fault probability;
* security risk;
* queue backlog and team load;
* observability quality;
* operational readiness;
* weather and access conditions;
* customer/SLA priority.

No post-treatment state may be included in the baseline adjustment set.

### 5.3 State vector

The dynamic state may include service impact, severity, affected customers, asset health, fault probability, security risk, topology criticality, redundancy, backlog, SLA time remaining, team load, weather/access, prior actions, escalation history, observability, and readiness.

### 5.4 Time scales

| Scale | Default |
|---|---:|
| Decision step | 15 minutes |
| Primary follow-up | 24 hours |
| Recurrence follow-up | 30 days, descriptive/simulation only |
| Portfolio simulation | 30 days |

## 6. Telecom roles and protocols

| Role | Responsibility |
|---|---|
| L1 / Front Office | Intake, classification, communication, basic diagnostics, SLA control |
| NOC | Network diagnosis, rerouting, failover, rollback, remote remediation |
| SOC | Security triage, enrichment, containment, isolation, residual-risk assessment |
| L2 / Back Office | Deeper investigation, correlation, remediation planning |
| L3 / Product Development and Lifecycle | Product/version defect analysis and durable-fix decisions |
| Field Operations | Physical inspection, safe repair, replacement, facility restoration |

| Protocol | V1 use |
|---|---|
| `MONITOR_REASSESS` | Primary comparison protocol; monitor and reassess under defined rules |
| `NOC_REMOTE` | Operational simulation and policy demonstration |
| `SOC_CONTAIN` | Operational simulation and policy demonstration |
| `L2_INVESTIGATE` | Operational simulation and policy demonstration |
| `L3_PRODUCT` | Operational simulation and policy demonstration |
| `FIELD_REPAIR` | Operational simulation and policy demonstration |
| `COORDINATED_RESPONSE` | Primary treatment protocol; fixed coordination bundle |

Eligibility is explicit and enforced. Unsafe field access or unauthorized security actions must make a protocol infeasible.

## 7. Structural data-generating process

The simulator separates:

| Component | Responsibility |
|---|---|
| Latent-factor model | Generates unobserved readiness, latent severity components, and other structural factors |
| Disturbance model | Generates exogenous incident types and initial conditions |
| Treatment assignment | Randomized or confounded assignment of the primary binary contrast |
| Observation model | Applies measurement error and observability limits |
| Missingness/censoring | Generates controlled missingness or incomplete follow-up scenarios |
| Transition model | Evolves the incident state after treatment |
| Resource model | Applies queues, capacity, and eligibility |
| Ground-truth oracle | Calculates potential outcomes for validation only |

Baseline DAG:

```text
Disturbance severity ──┬──> Treatment assignment ──> Outcome
                       ├──> Outcome
                       └──> Escalation need
Topology criticality ──┬──> Treatment assignment
                       └──> Outcome
Team backlog ──────────┬──> Treatment assignment
                       └──> Outcome
Operational readiness ─┬──> Treatment assignment
                       └──> Outcome
Treatment ─────────────> Post-treatment containment ───> Outcome
```

The DAG view must distinguish baseline variables from post-treatment mediators. V1 may explain mediation conceptually but does not estimate mediation effects.

## 8. Causal layer

Required estimators for the primary binary contrast:

* randomized difference in means;
* crude observational difference in means;
* stratified adjustment;
* outcome regression and standardization/g-formula;
* propensity-score diagnostics;
* IPW, with stabilized weights where appropriate;
* doubly robust estimation for supported static contrasts;
* transparent subgroup/CATE demonstrations;
* policy value estimation only where the required support and estimand are explicit.

Every result returns an `EstimateResult` containing estimand, population, estimate, uncertainty, method, assumptions, diagnostics, warnings, sample sizes, ground-truth comparison where permitted, and provenance.

## 9. Policy and allocation layer

The policy layer compares current-practice, severity-only, predictive-risk, causal-effect, value-per-resource, and teaching-only oracle policies.

For seven operational protocols, V1 reports structural policy simulation and constrained allocation results. It must label them as simulation/policy results, not as estimates of a multi-valued observational treatment effect.

Hard constraints include capacity, permissions, certification, field access and safety, security eligibility, budget, concurrent changes, queue/backlog, SLA priority, critical-service coverage, and fallback rules. Infeasibility must be reported explicitly.

## 10. DomainAdapter contract

```python
class DomainAdapter(Protocol):
    domain_name: str
    schema_version: str

    def generate_dataset(self, config: ScenarioConfig) -> CaseDataset: ...
    def define_target_trials(self) -> list[TargetTrial]: ...
    def list_actions(self, state: CaseState) -> list[Action]: ...
    def feasible_actions(self, state: CaseState, resources: ResourceState) -> list[Action]: ...
    def transition(self, state: CaseState, action: Action, rng: RandomGenerator) -> CaseState: ...
    def calculate_outcomes(self, episode: IncidentEpisode) -> OutcomeSet: ...
    def constraints(self, horizon: Horizon) -> ConstraintSet: ...
    def explain(self, recommendation: Recommendation) -> Explanation: ...
```

A future adapter must provide domain semantics, a domain DAG, a structural DGP with known ground truth, transitions, constraints, target-trial definitions, and contract tests without modifying the causal estimator APIs.

## 11. UI and visual language

Course mode contains 13 lessons. Sandbox mode exposes seed, sample size, disturbance mix, confounding strength, overlap, measurement error, missingness, capacity, policy objective, estimator, and adjustment-set controls.

Required visual language:

* blue: baseline/observed state;
* orange: treatment/action;
* green: improvement/containment;
* red: deterioration/warning/constraint violation;
* purple: latent or counterfactual information;
* gray: unavailable/censored/not identified.

Required views include incident timeline, DAG, balance, overlap, weights, estimates versus ground truth, subgroup effects, simulated counterfactual distributions, policy values, capacity/constraints, trade-off frontier, and assumption warnings. Plotly is mandatory; Graphviz is optional.

Every result view includes an analysis card: question, estimand, population, time zero, treatment, outcome, estimator, adjustment set, assumptions, diagnostics, uncertainty, interpretation, limitations, and provenance.

## 12. Python stack

Python 3.11+, Streamlit, Plotly, pandas or Polars, NumPy, SciPy, statsmodels, scikit-learn, DoWhy, EconML, Pydantic, and pytest. Versions must be pinned. R and Rust are excluded from V1.

## 13. Deferred methods

Instrumental variables, causal survival, mediation, time-varying treatment, treatment-confounder feedback, marginal structural models, g-estimation, and a second industry adapter are post-V1.
